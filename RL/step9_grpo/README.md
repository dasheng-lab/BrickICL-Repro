## 为什么直接做 GRPO（第 3 步的依据）

- GRPO 只需要组内奖励有差异：`|M| ≤ 10` 时 16 个样本里奖励不全相同的题占 42%（跳接 35%）。
  RFT 需要接近正确的样本，F1 ≥ 0.8 的样本只有 2.8%，跳接题关口（7.1% < 10%）没过。
- 主要差距在"放对"而不是"停对"：把每个样本截到 `|M|` 件重新打分，平均 F1 只从 0.058 升到 0.070。
- GRPO 每步都要重新采样，总采样量和第 4 步同一量级（500 步 × 约 1,000 个），所以必须换成 vLLM；
  HF `generate` 的 0.94 样本 / 秒下要 75 小时以上。
- `|M| > 10` 的题占一半采样时间，却几乎没有可用信号，不用。

## 做法（`grpo.py`）

每一步：

1. 取 64 道训练题（`common.sampling.prompts`，`|M| ≤ 10`，固定种子顺序），vLLM 用当前 adapter 每题采 16 个。
   协议同第 3 步和 step 11：温度 1、top-k 20、top-p 0.95，只在分词器的 EOS 处停（从第一个 token 起允许），
   最多 `64 (|M| + 4) + 32` 个新 token。
2. `common.rewards.completion` 打分（Pose F1，不能完整解析记 0），CPU 多进程。
3. 丢掉 16 个奖励全相同的组（梯度为 0）；保留的少于 16 组就再采一轮（最多 3 轮）。保留的组全部进入这一步。
4. 优势 = 奖励 − 组内均值（不除以组内标准差）；损失按 token 平均：`−A · log p + β · k3`，
   `k3 = exp(ref − log p) − (ref − log p) − 1`，`ref` 为关掉 adapter 的起点模型，β 默认 0.01。
   每批只更新一次，重要性比率恒为 1，不需要裁剪。
5. 保存 adapter，下一步 vLLM 换用它。

模型：起点 = Qwen3-0.6B + 官方 PT + `masked/checkpoint-2000`，由 `merge_start.py` 合并成一个普通 checkpoint
（与评测脚本同一个 `frozen.load`，bfloat16），在它上面训一个新 LoRA（r 32、alpha 32、7 个投影层，与 nzd 的 adapter 相同）。
第 7 步把 GRPO 组当作"起点 adapter + `checkpoint-<step>`"评测，和 RFT 组一样。

默认超参（未调过）：学习率 2e-5（预热 10 步，之后不变），AdamW，梯度裁剪 1.0，500 步。

## 第 1 轮（r1）监控与决策规则（2026-11-19 夜间，自主执行）

开发集噪声：各 checkpoint 用同一批 600 题、同一种子，比较是成对的；第 0 步逐题采样噪声约 0.003，
两个 checkpoint 之差的噪声约 0.004，所以 **开发集奖励变化 ≥ 0.01 才算真实**。第 0 步开发集奖励 0.087。
`monitor.py` 在出现新的开发集结果、训练停止、或最近 10 步均值越过警戒线（熵 < 0.08、KL > 0.05、
`n_p / n_t` < 0.8、保留组数 < 8、损失非有限）时返回。规则：

- 第 50 / 100 步开发集奖励比第 0 步高 ≥ 0.01：照常跑完。
- 第 100 步开发集提升 < 0.005 且 KL < 0.002（模型几乎没动）：学习率太小，从 `checkpoint-100` 续跑，学习率改为 5e-5。
  （`grpo.py` 续跑时现在以命令行的 `--lr` 为准；之前会沿用保存的优化器里的旧学习率。）
- 熵塌缩或 `n_p / n_t` < 0.8（只写一两件"稳妥"零件来刷分）：停下，保留到目前最好的 checkpoint，记录原因。
- 开发集连续两次比最好成绩低 ≥ 0.01：提前停，用最好的 checkpoint。
- 训练崩溃：查日志，修好后 `--resume` 续跑。

- 训练信号：KL 升到约 0.03 后稳定（第 275 步有一次尖峰 0.61、梯度范数 7.3，下一步即恢复，可考虑以后对每个 token 的 KL 项设上限）；
  熵 0.23 → 0.17 后回升到约 0.24，没有塌缩；每步保留约 28–30 组；每步约 140–150 s（显卡共用）。
### 为什么在第 401 步停

第 400 步开发集奖励 0.151，比最好（第 300 步）低 0.008，还没到"连续两次低 ≥ 0.01"的规则线，但三个信号同时变坏，
而且都远超噪声（每个 checkpoint 2,400 个样本）：

| 步 | 解析率 | 空补全（第一个 token 就是 EOS） | 平均生成件数 | 训练 KL（近 10 步） |
|---:|---:|---:|---:|---:|
| 0 | 0.646 | 0.168 | 9.08 | — |
| 300 | 0.743 | 0.182 | 4.95 | 约 0.03 |
| 350 | 0.720 | 0.191 | 4.69 | 0.035 |
| 400 | 0.621 | **0.269** | **3.11** | 0.050 |

- 解析失败的大头是空补全：第 400 步 2,400 个样本里 910 个解析失败，其中 543 个是空补全（第 300 步 617 个里 388 个）。
  写坏的零件行（连接器越界、零件没有对应连接器等）也从 229 个增加到 367 个。
- 判断：这是按 token 平均损失的长度偏差。空补全只有 1 个 token，负优势分到它身上的梯度极小；写了很多件却错了的长补全，
  每个 token 都被往下压。于是"少写 / 不写"的代价越来越低，`n_p / n_t` 从 1.5 降到 1.05，空补全从 18% 升到 27%。
  奖励里空补全记 0，所以这不是刷分，是优化方向上的偏差；再跑 100 步大概率继续变坏。
  （2026-11-21 修正：r1 的损失是"本批 token 损失之和 ÷ 本批 token 数"，同一步内分母是常数，梯度就是普通的策略梯度，
  并没有按样本长度加权的偏差。更准确的说法见下文"第 2 版"的"损失归一化"一行；结论不变：空补全的代价太低。）
- 处理：停止训练（`kill` 进程组，显卡已释放，没有动同事的任务），用 `checkpoint-300`。
  `checkpoint-400` 保留，需要的话可 `--resume` 跑完。

### 采样 Δlog-odds（sunshq 口径，2026-11-21）

上表的 ΔL 是 nzd step 11 的定义（给定的长 / 原答案按 teacher forcing 打分），**不是** sunshq 的定义。
`step7_eval/sampled_logodds.py` 按 sunshq `runs/structural_eval_20261115` 的协议重算（只读复用其输入、批次计划和 `score_results.py`）：
18 个 val 来源，"参照原样 / 参照加长"两个条件，每条件 4 次采样（温度 1、top-k 20、top-p 0.95，无 caption），
样本里补出的子树所含"多出来的那种零件"不少于长答案即算命中长特征；命中数 k 取 `ln((k+0.5)/(4−k+0.5))`，
加长减原样，对 18 个来源取平均，95% 区间按来源重采样。分"不给第一块 / 给第一块"两种。结果在 `runs/r1/eval/val/sampled_logodds/report.md`。

| | 起点（本次重跑） | GRPO 第 300 步 | GRPO − 起点（来源配对） | sunshq 表里的起点 |
|---|---:|---:|---:|---:|
| 不给第一块：Δlog-odds | +0.272 [−0.07, +0.67] | +0.422 [+0.15, +0.79] | +0.15 [−0.17, +0.47]（不显著） | +0.197 |
| 　命中长特征（原样 / 加长，各 72 个样本） | 4 / 8 | 0 / 6 | | |
| 　Pose F1（原样 / 加长） | 0.014 / 0.019 | 0.000 / 0.032 | | 0.014 / 0.012 |
| 给第一块：Δlog-odds | +2.705 [+1.92, +3.46] | +1.840 [+1.23, +2.53] | **−0.87 [−1.46, −0.25]** | +2.611 |
| 　命中长特征（原样 / 加长） | 5 / 50 | 0 / 29 | | |
| 　Pose F1（原样 / 加长） | 0.748 / 0.751 | 0.596 / 0.580 | | 0.724 / 0.750 |

- 核对：起点用同一批次、同一种子重跑，36 行里与 sunshq 的文件逐字相同的有 15 行（不给第一块）和 7 行（给第一块），
  其余在采样中途分叉（数值差异，合并方式 / 库版本不同），Δ 与 sunshq 的数在区间内一致。GRPO 与"本次重跑的起点"比较，两者流程完全相同。
- **按 sunshq 口径，GRPO 没有更跟参照**：不给第一块时差 +0.15（不显著）；给第一块时**显著下降** −0.87，
  加长参照下写出长特征的样本从 50/72 降到 29/72，Pose F1 也从约 0.75 降到约 0.59。
  与上面 teacher-forcing ΔL 的"升高"相反：那个升高只来自"参照原样"一项的答案概率下降，不是更会按加长参照写长。
- 每条件只有 4 个样本、18 个来源，区间较宽；给第一块那一项的下降区间不含 0。

**为什么变差：主要是 GRPO 学会了早停。** 给第一块时，从 `p1.{masked,grpo}.scored.jsonl` 统计（每条件 72 个样本）：

| | 写出零件数 | 目标零件数 | 写得比目标短 | 多出来那种零件的个数（命中阈值 6.8） | 命中长特征 |
|---|---:|---:|---:|---:|---:|
| 起点，参照原样 | 8.4 | 2.8 | 11% | 4.5 | 5 / 72 |
| 起点，参照加长 | **12.5** | 6.8 | 14% | **8.8** | **50 / 72** |
| GRPO，参照原样 | 5.0 | 2.8 | 28% | 2.4 | 0 / 72 |
| GRPO，参照加长 | **7.2** | 6.8 | **46%** | **4.65** | **29 / 72** |

- 起点模型严重写长（参照加长时写 12.5 件，目标 6.8 件），很多命中是靠写长越过阈值；写多了不扣分（"不少于"即命中），
  所以起点的 +2.7 有一部分来自写长，而不是认真照着参照写。
- GRPO 的奖励是 `|M| ≤ 10` 目标上的 F1，写多会降低精确率；token 平均的损失又让很短 / 空的补全代价很小（第 401 步停训的原因）。
  于是它写的长度接近目标（7.2 对 6.8），但 46% 的样本停在目标之前，越过阈值的从 50 个降到 29 个。
- 它仍然对参照有反应：参照加长时写得更多（5.0 → 7.2 件，多出的零件 2.4 → 4.65），与起点的反应比例相近（8.4 → 12.5）；
  是整体变短，再经过"命中 / 不命中"的阈值，Δ 才降下来。
- 训练里没有任何东西要求"照着加长的参照写出长腿"：训练题里没有加长参照；longleg 题上自己停的奖励也只是 0.030 → 0.054（不显著）。
- Pose F1 的下降同一个原因：它只看前 n_t 件，GRPO 写得比目标短的样本占 28–46%（起点 11–14%），召回率下降。
- 下一轮：去掉偏向写短的因素（按序列平均损失，或给空 / 不可解析的补全 −0.1，见"下一轮可以改的"）；
  奖励里召回率权重大于精确率（如 β > 1 的 F-beta），让早停比写多代价更大；加上训练集里的"加长参照"题，直接奖励跟参照。

## 第 2 版（v2）方案（2026-11-21；代码写好并在 CPU 上核对，未训练，等 GPU）

依据是上面 r1 的三个问题：(1) 越训越早停，第 300 步后空补全变多；(2) 给第一块、参照加长时 46% 的样本停在目标之前，
sunshq 口径的 Δlog-odds 从 +2.7 降到 +1.8；(3) 训练里没有任何东西奖励"照着参照写"。
`run_grpo.sh` 用 `PRESET=v2` 打开下面的改动；`grpo.py` 的默认值仍是 r1（r1 可以原样复现）。

| 改动 | r1 | v2 | 针对 |
|---|---|---|---|
| 奖励 | Pose F1 = 2m / (n_p + n_t) | **F2** = 5m / (4 n_t + n_p)（`--beta 2`） | 早停：漏一件的代价约是多写一件的 4 倍 |
| 解析失败 / 空补全 | 0（与写了但全错相同） | **−0.1**（`--fail-reward -0.1`） | 空补全代价太低 |
| 损失归一化 | ÷ 本批 token 数 | **÷ 固定的 70,000**（`--loss-norm const`，r1 第 1–50 步的中位数） | 输出变短时步长变大 |
| 训练题 | 只有普通补全题（`|M| ≤ 10`） | 每轮 64 题里 **16 道加长参照题**（8 对，`--stretch-frac 0.25`） | 没有奖励"跟参照"的信号 |
| 开发集 | 600 题 × 4 | 另加 **加长参照开发集**（187 对 × 4），每个 checkpoint 报 Δlog-odds | 选 checkpoint 时能看到这一点 |
| 监控 | 熵、KL、`n_p / n_t`、保留组数 | 另加空补全 > 0.25、停在目标前 > 0.5 报警 | 第 401 步那种漂移 |

学习率 2e-5、KL 0.01、LoRA r32、每题 16 个样本、500 步、每 50 步存档，都与 r1 相同（一次只改针对问题的部分）。

**奖励 F2。** 漏写和多写在 F1 里代价相同；F2 里漏写贵得多。最优仍是正好写完 M：全对时多写 4 件，k = 3 得 0.79，
不会无限写长；撞到 token 上限的样本通常停在半行，解析失败，得 −0.1，所以不会退回起点模型那样写到上限（val 上撞上限 17%）。
加长参照开发集上，把目标截掉 r 件：F2 0.590，F1 0.687，F2 对"少写"罚得更重。

**用 v2 的奖励给 r1 的开发集重新打分**（`check_v2.py`，600 题 × 4，同一批样本）：

| 步 | r1 奖励（F1） | v2 奖励（F2，失败 −0.1） | 空补全 | 能解析但停在目标前 | `n_p / n_t` |
|---:|---:|---:|---:|---:|---:|
| 0 | 0.087 | 0.059 | 0.168 | 0.160 | 2.72 |
| 100 | 0.139 | 0.121 | 0.198 | 0.225 | 1.66 |
| 300 | 0.159 | 0.138 | 0.182 | 0.251 | 1.53 |
| 400 | 0.151 | 0.114 | 0.269 | 0.257 | 1.05 |

第 300 → 400 步，F1 只降 0.008（在"连续两次低 0.01"的停训线以内），v2 奖励降 0.024，**早停漂移在 v2 的奖励下是看得见的**。
r1 并没有只是靠变短涨分：在 v2 的奖励下第 0 → 300 步也涨了 0.079。

**损失归一化（修正 r1 的判断）。** r1 的损失是"本批所有 token 的损失之和 ÷ 本批 token 数"。同一步里分母是常数，
所以梯度就是普通的策略梯度 Σ A_i ∇log π(y_i)，并没有按样本长度加权的偏差。真正的问题有两个：
- 空补全的负优势只落在一个 EOS token 上；而每个写错的长补全都在压低自己的"继续写"token，等于在所有位置上抬高 EOS。
  两者都来自奖励：空补全和写了但全错一样得 0。所以主要的修正放在奖励（−0.1），不在归一化。
- 分母随输出变短而变小（r1 第 1–50 步中位数 71k token，最后 50 步 59k），正好在变短的时候有效步长变大约 20%。
  固定分母去掉了这一点；取 70,000 让开头的步长与 r1 相同。

`--loss-norm seq`（原始 GRPO：每个样本先在自身 token 上平均）也在代码里，它对短样本加权大得多，压空补全更狠，
但按 Dr. GRPO 的分析它也偏向写长的错答案，所以不作默认，只在 v2 仍出现空补全上升时作对照。

**加长参照题（`build_stretch_prompts.py`）。** 做法与 nzd 第 8 / 11 步的长腿题相同（只读载入 `build_longleg.held_out_row`
和 `brickicl.sampling.edits.stretch`）：有重复、可加长的肢体的模型，留出一份作 M，另一份放在前缀最后作参照。
每一份都同时写成两种条件，**成对放进同一轮**：

- 加长：所有副本都加长 r 件，M = 加长后的那份；
- 原样：模型如数据集，M = 原来那份。

两种条件的 M 都与上下文一致（与第 11 步的"原样"条件不同，那里 M 故意与参照不符）。同一个模型、同一个位置，
目标长度只能从参照读出来。r 每份随机取 1–5，模型要数，而不是学"多写 4 件"。奖励就是普通的 F2，不另加长度项。

只用 sft 的模型（val 一个都不读，sunshq 和第 11 步的长腿测试都在 val 上）：

| 集合 | 来源 | 结果 |
|---|---|---|
| 训练 `runs/stretch/train.jsonl` | `sft_train_v2` 的 10,000 个模型，加 40,000 个其他 sft 模型；去掉开发集的模型和 `sft_dev_v2` | 2,083 对（1,081 个模型），与开发集、`sft_dev_v2` 无重叠 |
| 开发 `runs/stretch/dev.jsonl` | 训练池以外的 4,000 个 sft 模型 | 187 对（98 个模型） |

只有 2–4% 的模型有可加长的肢体，所以要加训练池以外的模型；只用训练池是 473 对、243 个模型，400 步要重复约 7 遍，
现在约 1.5 遍。r 1–5 各约 400 对，加长后的 M 3–14 件。
多数题参照在前缀最后（开发集 355 / 374）、多数是跳接（338 / 374），与 val 的长腿题相同。

**开发集上的加长参照检查。** 每个 checkpoint 在加长参照开发集上每题采 4 个：两种条件下的长特征命中率
（写出的"多出来那种零件"不少于加长后的 M，sunshq 的规则）、sunshq 公式的 Δlog-odds（按对平均），以及停在目标前的比例。
这里数的是所有生成零件里那种零件的个数，sunshq 数的是生成的子树里的，只作训练中的监控；
val 上的数仍用 `step7_eval/sampled_logodds.py` 按 sunshq 的协议算。核对：用目标本身作答案，命中率加长 1.0、原样 0.0，
Δlog-odds = 2 ln 9 = 4.39，与公式一致。

**CPU 核对（`check_v2.py`，全部通过）。** β = 1、失败 0 时与 r1 存下的奖励完全相同（800 个样本，最大差 0）；
三种归一化的梯度与逐 token 手算一致（最大差 1e-9）；加长参照题的打分、命中和 Δlog-odds 如上。

### v2 的判定标准（训练前写下）

与起点（`masked`）和 r1 的 `checkpoint-300` 比，val 上：

- sunshq 口径、给第一块的 Δlog-odds 不低于起点（+2.7；r1 +1.8），参照加长时停在目标前的比例 ≤ 25%（r1 46%，起点 14%）；
- 强制长度 pass@1 不低于 r1（0.083）减噪声，自己停的 val 奖励（F1）不低于 0.14（r1 0.151）；
- 开发集空补全一直 ≤ 0.2（r1 第 400 步 0.27）。

checkpoint 按开发集的 v2 奖励选（`select_checkpoint.py --beta 2 --fail -0.1`，同时列出 F1），加长参照开发集的数一并报告。
停训规则同 r1，另加：开发集空补全连续两次 > 0.25 就停。

### 还没解决的

- **从零搭建变短**（有效长度 35.6 → 11.7）：v2 仍只训练补全题。F2 和 −0.1 应当减轻早停，但不直接奖励从零搭得长；
  如果 v2 的第 7 步评测里这一项仍明显退步，下一步在训练里混入少量从零搭建题（奖励 `rewards.generation` 的 `reward_len`）。
- 每个 token 的 KL 上限没有加（r1 第 275 步的尖峰下一步就恢复了）。
- 失败奖励会让更多组"组内有差异"（全错但有的解析失败），每步训练的样本会变多，速度要在试跑里量。

### 自主执行规则（2026-11-21 使用者授权：v2.1 跑完后自动分析、优化，接着跑下一组，不再逐次请示）

始终不动同事的任务；每次只有一个我们的 GPU 任务；每一步决定都记在本节下面的"记录"里。

**v2.1 训练中**（每 50 步一次开发集，`monitor.py` 出现结果或报警时检查）：
- 照常跑完 400 步，除非：开发集 F1 奖励（给第一块）连续两次比最好低 ≥ 0.01；或开发集空补全连续两次 > 0.25；
  或熵 < 0.08 / `n_p / n_t` < 0.8 持续 10 步 —— 这时提前停，用最好的 checkpoint。
- 训练崩溃：查日志，修好后 `--resume`。

**v2.1 跑完后**：
1. checkpoint 按开发集 F2 奖励选（`select_checkpoint.py --beta 2`），与 r1 同步的给第一块对照逐项比（F1 奖励、停在目标前、空补全、
   加长参照的命中和 Δlog-odds）。
2. val：选中的 checkpoint 跑 sunshq 口径的采样 Δlog-odds（给 / 不给第一块），再跑第 7 步评测（强制长度、自己停、独立搭建、ΔL）。
3. 下一组只在"目前最好的一组"上加一处改动：
   - v2.1 达标，或停在目标前降了但加长参照的命中没涨 → **v2.2 = v2.1 + 25% 加长参照题**（同样给第一块）；
   - 停在目标前没降、或空补全升高 → **v2.2 = v2.1 + 解析失败 / 空补全 −0.1**；
   - v2.1 的开发集 F1 奖励比 r1 同步低 ≥ 0.01（F2 有害）→ 下一组回到 F1，只加 25% 加长参照题。
4. 最多再自动跑 3 组（约 3 天 GPU），或连续两组主指标（val 上给第一块的采样 Δlog-odds）都没有超过目前最好的一组，就停下来汇报。
