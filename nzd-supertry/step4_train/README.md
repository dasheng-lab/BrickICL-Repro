## 试跑发现：官方训练数据是深度优先顺序（2026-11-10）

试跑时冻结的官方 PT 在我们开发集上的起始 loss 是 0.70（掩码）和 0.75（普通），只训 25 步就掉到 0.42 和 0.44。
普通顺序本该是官方模型最熟悉的数据，不应该这样。追查后的结论：

- **官方发布的序列全部是深度优先顺序。** 每个零件都接在上一个零件或它的某个祖先上。
  sft 和 val、全部 5 轮采样，抽查的 800 条序列 100% 满足。
- **官方公开的采样函数 `sample_collision_free_tree` 不是这个顺序。** 它按随机边界游走的访问顺序写出，
  只有 44% 的零件满足上面的条件。
- **两者的生成树形状几乎一样**（根的子节点数 2.2 对 2.1，叶子比例都是 0.45）。
  所以官方数据相当于"用公开采样器选出树，再把这棵树按深度优先重写"。

冻结的 BrickNet-0.6B-PT 在同一批模型上的 loss（每 token，`check_order_loss.py`）：

| 序列 | sft（150 个开发模型） | val（150 个模型） | 结束符的 loss（sft / val） |
|---|---:|---:|---:|
| 官方自带的序列 | 0.266 | 0.281 | 1.09 / 0.80 |
| 公开采样器的原始顺序（第 3 步的对照组） | 0.716 | 0.702 | 5.81 / 5.37 |
| 同一棵树按深度优先重写，子节点按放置顺序 | 0.273 | 0.286 | 4.63 / 4.52 |
| 同上，子节点按放置的逆序 | 0.273 | 0.282 | 3.82 / 2.82 |
| 同上，子节点随机 | 0.274 | 0.285 | 4.93 / 4.53 |

权重加载方式（bf16 合并、fp32 合并、不合并）对结果没有影响，差别完全来自顺序。

**对本实验的影响**

- 第 3 步最初的数据（`v1`）两组都是边界游走顺序，对官方模型来说都是分布外的。直接训练的话，两组都会先花力气学"边界游走顺序"，
  这个共同的变化会盖过我们想比较的差别。
- 已修正：两组都改成深度优先（`v2`）。对照组是树的先序遍历；增强组是同一棵树，把 `M` 那棵子树挪到最后。
  两组用同一棵树、同样的连接，唯一的差别是 `M` 的位置。冻结模型在 `v2` 对照组上的 loss 是 0.250，已在训练分布内，
  详见[第 3 步](../step3_data/README.md)。
- 深度优先顺序下，"回到一个不在当前路径上的早期零件接新结构"在官方训练数据里从不出现。
  掩码顺序恰好引入这种情况，所以这个增强相对官方数据的新意比原先估计的更大。

**还没弄清的**

- 重写后的序列主体已经和官方数据一致，但结束符的 loss 仍比官方序列高（2.8–4.9 对 0.8–1.1）。
  官方序列的结尾有某种我们没复现的规律；子节点的次序按零件编号、接口编号、子树大小、度数检验都是随机的。
- 官方序列的根零件度数略高（2.68 对 2.09），说明根不是完全均匀随机选的。

**对之前结果的影响**

`brickicl/sampling/masked_walk.py` 也是边界游走顺序，所以之前在冻结 BrickNet 上做的试点、长腿和两轮探针，
前缀对模型来说都是分布外的。"副本连续写出时才跟随上下文"这个现象，很可能部分来自连续写法更接近深度优先。
这些结论需要在深度优先的前缀上重测后才能确认。

|---|---|---|
| 增强 `masked` | `sft_train_v2/masked.jsonl` | `sft_dev_v2/masked.jsonl` |

## 官方脚本做什么

`pt` 模式下：

1. 从 jsonl 里取每行的 `path`（一条搭建序列的文本）。
2. 用 Qwen3 的分词器现场分词，超过 6400 个 token 的截断，末尾加结束符。
3. 加载 Qwen3，把 `--pt_adapter` 指定的 adapter 合并进去，再新建一个空的 LoRA，只训练它。
4. 训练目标是预测下一个 token，序列里每个位置都算 loss（按 token 平均），不带文字描述。
5. 定期在验证集上算 loss、存 checkpoint，结束时把 LoRA 存到 `输出目录/adapter`。

## 我们改了什么

官方配方写死在脚本里，是为"从零训练 25 万步"设计的。`train.py`（本目录）是一个很薄的启动脚本：
它导入官方脚本，只替换下面几个数，然后调用官方的训练入口。`baseline/` 里的官方代码没有改动。

| 项目 | 官方 PT | 这里 | 原因 |
|---|---|---|---|
| 起点 | 裸 Qwen3 | Qwen3 + 官方 BrickNet-0.6B-PT | 我们做的是后训练 |
| 步数 | 250,000 | 2,211 | 70,722 条 ÷ 32，正好一轮 |
| 学习率 | 5e-4 | 1e-4 | 起点已经训好，大学习率容易冲掉原有能力 |
| 预热 | 12,500 步（5%） | 111 步（5%） | 保持官方的比例 |
| 验证间隔 | 2,500 步，抽 1,000 条 | 250 步，开发集全部 2,133 条 | 一轮里要能验证多次 |
| 保存 | 5,000 步，留最近 3 个 | 250 步，全部保留 | 按开发集 loss 挑 checkpoint |
| 每次前向的条数 | 32 | 8，累积 4 次再更新 | 一次 32 条在单张 H20 上超过 96 GB；等效 batch 仍是 32 |
| `torch.compile` | 开 | 关 | 集群的 torch 2.14.1 上与 Liger 算子冲突，只影响速度 |
| 第 0 步验证 | 无 | 有 | 得到冻结 PT 在开发集上的起始 loss |

保持官方不变的：LoRA（r=32，alpha=32，作用在 q/k/v/o 和前馈层的三个矩阵）、等效 batch 32、AdamW（权重衰减 0.033）、
梯度裁剪 1.0、余弦下降到 1%、bf16、最大长度 6400。

梯度累积有一个坑：官方脚本自己算 loss，而训练框架会误以为这个 loss 已经按累积批次归一化，
把 4 次前向的 loss 直接相加，梯度变成 4 倍。启动脚本里设了 `loss_is_scaled_for_ga = False` 来纠正。

**试跑的速度和显存**（在 `v1` 数据上跑 60 步）：每步约 1.2 秒，显存峰值 36 GB；在开发集全部条目上验证一次约 74 秒。
按此估计一组约 1 小时，两组约 2 小时。

和队友的后训练（`dasheng/unified-eval-and-viewer` 分支）相比有两点不同：官方按 token 平均 loss，他们按样本平均；
官方 LoRA 是 r=32，他们是 r=16。所以和他们的结果不是严格同配方，本目录两组之间才是严格可比的。

## 运行

在集群的仓库根目录。环境里需要 `liger-kernel`（`pip install liger-kernel==0.8.5`，2026-11-10 已装）。

```bash
source brickicl/env.sh
mkdir -p logs
nohup bash nzd-supertry/step4_train/run_both.sh > logs/nzd-supertry.train_v2.log 2>&1 < /dev/null &
tail -f logs/nzd-supertry.train_v2.log
```

`run_both.sh` 先训增强组，再训对照组，输出到 `runs/nzd-supertry/train_v2/{masked,plain}/`。单独训一组：

```bash
python nzd-supertry/step4_train/train.py --arm masked --output runs/nzd-supertry/train_v2/masked
```

GPU 是共享的，启动前先用 `nvidia-smi` 确认没有队友在用。

## 输出

每组的输出目录里：

| 文件 | 内容 |
|---|---|
| `run_config.json` | 参数、实际用的配方、数据文件的 SHA-256、代码提交号、开始时间 |
| `checkpoint-<步数>/` | 每 250 步一个 LoRA checkpoint，含 `trainer_state.json`（训练和开发集 loss 的记录） |
| `adapter/` | 训练结束时的 LoRA |
| `summary.json` | 用时、开发集 loss 曲线、loss 最低的步数 |
| `scratch/` | 分词前的文本缓存，可以删 |

本目录另有 `check_order_loss.py`：用冻结模型的 loss 判断一种序列顺序是否在官方训练分布内。
`orders` 模式算出上面"试跑发现"的表，`pool` 模式检查一个数据池的两组。

## 加载训练好的权重

新的 LoRA 不能单独叠在裸 Qwen3 上，要先恢复训练时的起点：

```python
import torch
from peft import PeftModel
from transformers import AutoModelForCausalLM

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-0.6B", dtype=torch.bfloat16, device_map="auto")
model = PeftModel.from_pretrained(model, "kulits/BrickNet-0.6B-PT").merge_and_unload()
model = PeftModel.from_pretrained(model, "runs/nzd-supertry/train_v2/masked/checkpoint-2000").merge_and_unload()
```

`brickicl/eval` 里的脚本支持重复传 `--lora`，按顺序合并，评测时依次传官方 PT 和我们的 checkpoint 即可。
